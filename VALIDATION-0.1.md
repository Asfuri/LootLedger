## Reported detection failure — 5 November 2026

Before the recording was supplied, the user reported that no chests were detected after completing all three setup steps. Inspection of the saved profile confirmed that its required references, resolution and interaction-circle selection were present. The initial inspection did not establish which live stage failed; the subsequently supplied footage and measured failure are documented below.

A controlled diagnostic using the saved closed-chest crop reproduces a fundamental appearance limitation. The existing matcher finds the unchanged crop at two different positions (score 0.9999), but misses it at half size (0.3187), 1.5 times size (0.3230), and after a 15-degree image rotation (0.4840), against the configured 0.82 threshold. These are artificial transforms of one real crop, not held-out gameplay, and cannot supply opening accuracy or explain which gate failed during the user's game. Results: [template diagnostic](validation/detector-design-diagnosis.json).

Source inspection also confirms that only three template scales are searched, the search/progress regions remain fixed, and an appearance match against the saved HUD crop is mandatory before chest tracking. Repeating the guide cannot make this a general chest recognizer. Merely lowering thresholds risks false matches and does not resolve state association or personal attribution.

The next implementation should replace the appearance/state stage with a local detector trained on labelled closed/opened chests across varied views, and locate the associated interaction indicator as it moves. Retain temporal completion proof, chest-specific XP corroboration, uncertain-event review and the real-footage validation gate. The initial diagnosis requested a clip reproducing the missed openings; that clip has now been supplied and analyzed below. Representative training footage and separate validation footage remain necessary. This initial image-transform diagnosis made no detector change; the later notification-parser correction is documented separately.

## Gameplay validation — failed baseline

The user supplied **Battle Royale Build Unranked Duo - 40 Left.mp4** on 5 November: 1920×1080, 608 frames, approximately 29.996 FPS, duration 20.269 seconds. Visual inspection found four completed personal chest openings at approximately **1.6, 10.6, 11.8 and 17.4 seconds**. The close pair is about 1.2 seconds apart; its reward label changes from CHEST to CHEST X2 while XP rolls upward. These timestamps were labelled from observed search progression and before/after chest states, not calculated from XP amounts.

The original complete offline pipeline analyzed **178 sampled frames** with the saved user profile and normal same-aspect resizing to 2560×1440. It generated **zero confirmed events and zero review events**: **0 matched, 4 missed, 0 false and 0 duplicate counts**, with the gate false. All 178 observations were inactive. Independent ungated checks at 17 representative timestamps found HUD match scores of **0.625–0.732**, closed-chest scores of **0.348–0.431**, and opened-chest scores of **0.275–0.459**, all below the configured 0.82 threshold. This establishes failure on this clip; zero false counts from a detector producing nothing is not evidence of useful specificity. A SIFT/homography probe also failed to provide usable geometric chest recognition, so it was not installed as a replacement.

The source parser/tracker now accepts the exact CHEST award multiplier and does not treat animated XP amounts as new awards. A separate **notification-only** sweep using actual Windows OCR on all 178 sampled crops followed four stable award tokens, first available at **2.305, 11.402, 12.139 and 18.203 seconds**. These are OCR-evidence availability times, not opening timestamps. This run does not recognize chests, establish personal attribution, or confirm openings. The complete detector remains unsuccessful because its HUD/appearance stages are unchanged. The parser fix is source-only; no new executable was installed during this investigation. All reports retain `release_gate: false` and no events were imported into the ledger.

The original complete sweep took 300.53 seconds while other diagnostics were running. The subsequent notification-only sweep took 102.38 seconds. These are offline run times, not controlled live-capture benchmarks; real-time throughput remains unproven and needs optimization and measurement alongside recognition.

## Release behavior and failure plan

Fresh installs open **Quick setup** with no reference images. The supplied screenshot was prepared only in this user's local setup; it is not bundled as game artwork. The guide saves each step, defaults types to Unknown, and requires an opened-chest reference before review tracking. After setup it can generate review items. It enables automatic confirmations only when the attached report matches the profile/reference-content fingerprint and passes the documented minimum real-footage gate. There is no manual-counter fallback disguised as successful automatic tracking.

The existing implementation has failed the supplied real footage. Keep automatic totals disabled. Replace the weak appearance/state stage and fixed interaction-location stage with a locally trained detector using labelled closed/opened boxes and interaction states, evaluate on separate footage, and retain temporal personal-interaction proof and exact chest-XP corroboration. Additional dashboard features cannot resolve this detection failure. Validation fingerprints include the detector revision as well as the profile/reference contents.
